# 구조와 실행 흐름

## 1. 실행 시작

`python -m budget_app`은 `__main__.py`를 실행한다. 이 파일은 `cli.main()`의 반환값을 `SystemExit`에 전달한다. 사용자 입력부터 파일 순회와 출력까지 `@handle_cli_errors` 안에서 실행되어, 정상은 0이고 오류는 비0으로 종료된다.

`cli.py`는 위에서부터 import → 사용자 정의 ArgumentParser → 옵션 파서 → build_parser → prompt → 출력 함수 → 대화형 add → main 순이다. 함수 정의를 읽는 순서와 실제 호출 순서는 다르다. 실제 명령 실행은 main에서 시작한다.

## 2. 모델과 검증

`models.py`의 Transaction은 거래 한 건, MonthlyBudget은 월 예산이다. SearchFilter는 검색 조건과 matches 판단을, MonthSummary는 집계 결과와 잔액·초과 여부·사용률을 표현한다.

모델은 `dataclass(frozen=True)`로 정의한다. `__post_init__`에서 값 자체를 검사하고, 수정은 `dataclasses.replace`로 새 객체를 만들어 재검증한다. frozen은 메모리 객체 변경을 제한하는 기능이지 파일 저장의 원자성을 보장하지 않는다.

`validators.py`는 날짜 모양과 실제 존재 여부, 양수 정수 금액, 허용된 타입, 문자열 및 태그를 검사한다. 입력 문자열을 정수로 바꾸는 parse_amount와 정수의 유효성을 확인하는 validate_amount를 구분한다. bool은 int의 하위 타입이지만 금액으로는 거부한다.

## 3. 서비스 책임

`BudgetService`는 화면이나 input을 처리하지 않는다. 등록된 카테고리인지, 삭제 가능한지, 수정할 거래가 있는지, 월별 합계가 얼마인지 판단한다. 저장소가 읽어 준 거래와 모델의 검증을 연결한다.

`_inspect`는 거래 파일 변경 전 ID 집합을 만들어 전역 중복과 카테고리 참조를 확인한다. 이 집합은 조회에는 만들지 않는다. 모든 예산·카테고리 쓰기에도 실행하는 것은 아니다.

## 4. 저장소와 원자적 교체

`TransactionRepository`는 거래를, `CategoryStore`는 카테고리를, `BudgetStore`는 예산을 관리한다. `DataStore`는 경로·초기화·잠금·보호 경로를 다룬다.

`atomic_text`는 원본과 같은 디렉터리에 임시 파일을 만든다. 전체 결과를 쓴 뒤 flush → fsync → 닫기 → os.replace를 수행한다. 교체 전 예외에서는 원본을 유지한다. `_rewrite`는 수정할 원래 거래를 제외하고 수정 사본을 정렬 위치에 끼워 넣는다. 삭제에서는 원래 거래를 제외하기만 한다.

잠금은 동시 작업의 충돌 방지, 원자적 교체는 중간 결과 노출 방지를 담당한다. 둘은 다른 문제다. 입력 대기 중에는 잠금을 잡지 않고 실제 저장 전 카테고리 상태를 다시 확인한다.

## 5. 스트리밍과 최신순

읽기 흐름은 `iter_jsonl → iter_transactions → _checked_transactions → search → print_transactions`다. 각 단계는 거래를 하나씩 넘긴다. 제너레이터 함수는 호출만으로 본문 전체를 실행하지 않고 다음 값이 요구될 때 실행한다.

거래 파일은 `(date, id)` 내림차순으로 유지하므로 조회에서 전체를 다시 정렬하지 않는다. 날짜가 같을 때 ID 정렬은 등록 시각순이 아니다. limit에 도달하면 더 읽지 않으며, closing으로 조기 종료에도 열린 파일과 잠금을 정리한다. 따라서 limit 뒤에 있는 손상은 그 조회에서 발견하지 못할 수 있다.

## 6. CSV 전체 미반영 정책

`csv.DictReader`가 헤더·쉼표·따옴표를 처리한다. tags 필드만 추가로 쉼표 분리한다. 모든 신규 행을 검증한 뒤 정렬하고, 기존 거래 스트림과 heapq.merge로 합쳐 한 번 교체한다.

한 행이라도 잘못되면 기존 거래 파일을 변경하지 않는다. 오류 위치는 레코드의 마지막 물리 행 기준이다. CSV에는 ID가 없으므로 새 ID를 부여하며, 같은 CSV 재가져오기는 내용 중복을 추가할 수 있다.

## 7. 데코레이터

`handle_cli_errors`는 CLI 공통 오류 처리를 분리한다. AppError에는 원인·힌트·종료 코드가 있다. functools.wraps는 원래 함수의 이름·문서·주석 정보를 유지한다.

파일 순회 중에야 발생하는 지연 오류도 잡으려면 제너레이터 생성만이 아니라 실제 순회와 출력까지 감싸야 한다. 이 구현에서는 main 전체가 그 경계다. stdout이 닫힌 파이프 오류와 EOF/Ctrl+C도 구분한다.

## 8. 타입 힌트

`Literal["income", "expense"]`는 거래 타입, `Iterator[Transaction]`은 한 건씩 내보내는 반환 계약, `TypedDict`는 CSV에서 읽은 필드 구성을 표현한다. ParamSpec은 데코레이터가 감싼 함수의 인자 타입을 이어 주기 위해 사용한다.

타입 힌트는 런타임 입력을 자동 검사하지 않는다. JSON에서 읽은 값을 cast한다고 실제 값이 변환되거나 검증되는 것도 아니다. 실제 유효성 검사는 모델과 validators에서 한다. 외부 정적 타입 검사기는 이번 검증에 사용하지 않았다.

## 9. 10만 건 병목과 한계

n은 기존 거래 수, m은 가져올 거래 수, c는 카테고리 수다.

| 작업 | 핵심 비용 |
|---|---|
| list K건 | 최대 K건 거래 소비와 카테고리 로딩 |
| search·summary | 전체 거래 O(n) 순회, 요약의 카테고리 집계·정렬 비용 추가 |
| add/update/delete | O(n) 검사·재작성, ID 집합 O(n) 메모리 |
| import | 신규 정렬 O(m log m), 병합 O(n+m), 메모리 O(n+m) |
| export | O(n) 순회, 결과는 한 건씩 CSV로 작성 |

월별 파일 분할·색인·외부 병합 정렬은 개선 제안이며 구현된 기능이 아니다. 단일 파일 교체는 정전 내구성·여러 파일 트랜잭션·외부 편집기 변경까지 보장하지 않는다.
