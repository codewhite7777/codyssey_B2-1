# 코드 흐름 해설 — 입력 한 건이 저장되고 다시 출력되기까지

실행 준비는 [README](../README.md)를 먼저 확인합니다. 여기서는 현재 소스의 실제 함수 이름을 따라갑니다. 코드를 위에서 아래로 읽는 순서와 런타임 호출 순서를 구분하고, 프로그램 기능을 늘리는 대신 기존 구현의 이유를 이해하는 것이 목적입니다.

## 1. 전체 구조: 누가 무엇을 담당하는가

| 계층 | 파일 | 책임 | 하지 않는 일 |
|---|---|---|---|
| 시작점 | `__main__.py` | CLI를 호출하고 종료 코드를 전달 | 입력·저장·합계 계산 |
| CLI | `cli.py` | 명령 해석, 대화형 입력, 결과 출력 | JSONL 직접 변경 |
| 서비스 | `service.py` | 거래 등록·수정·검색·집계의 업무 규칙 | `input()`·화면 출력 |
| 모델 | `models.py` | 거래·예산·검색 조건·요약의 데이터 구조 | 카테고리 파일 조회 |
| 검증 | `validators.py` | 값 변환과 형식·범위 검사 | 파일 저장 |
| 저장소 | `storage.py` | 파일 읽기·쓰기·잠금·초기화 | 사용자에게 질문하기 |
| CSV | `csv_io.py` | CSV 스키마·행 변환·열 인코딩 | import 성공 시점 결정 |
| 오류 | `errors.py`, `decorators.py` | 원인·힌트 전달, CLI 오류 변환 | 저장된 거래의 자동 롤백 |

`models.py`와 `validators.py`는 여러 계층에서 사용합니다. 무조건 모든 명령이 모든 계층을 한 번씩만 거치는 직선 구조는 아닙니다. `__init__.py`는 패키지 설명과 버전만 제공하며 프로그램을 자동 실행하지 않습니다.

## 2. 프로그램이 시작되고 끝나는 순서

명령:

```bash
python3 -m budget_app --data-dir ./data/practice list --limit 5
```

1. Python이 패키지를 찾아 `__main__.py`를 실행합니다.
2. `from .cli import main`이 CLI 모듈을 읽습니다. `def`는 함수 객체를 정의하지만 본문을 당장 실행하지 않습니다. 데코레이터 적용은 이 정의 시점에 일어납니다.
3. `main()`을 호출하면 실제로는 `@handle_cli_errors`가 반환한 `wrapped`가 호출됩니다.
4. `wrapped`의 `try` 안에서 원래 `cli.main`을 실행합니다.
5. `build_parser().parse_args(argv)`가 옵션을 `Namespace`로 만듭니다. 이 예에서는 `command='list'`, `limit=5`, `data_dir=Path('data/practice')`입니다.
6. `BudgetService`가 저장 경로를 준비합니다. 실제 파일 접근은 서비스 메서드의 `session`이 시작될 때입니다.
7. 목록 결과를 출력하고 `main`이 0을 반환합니다. 오류가 났다면 `wrapped`가 다른 정수를 반환합니다.
8. `SystemExit`가 그 정수를 프로세스 종료 코드로 사용합니다. 셸로 돌아오면 다음 명령을 새로 실행합니다.

`--help`는 argparse가 도움말을 출력하고 정상 종료하므로 서비스를 만들지 않습니다. 필수 명령을 생략하는 것은 메뉴 진입이 아니라 사용법 오류입니다. `argv=None`이면 실제 터미널 인자를 사용하고, 테스트에서는 문자열 목록을 전달해 명령을 재현할 수 있습니다.

## 3. 거래 추가: 입력에서 파일까지

`cli.main → _add → prompt → BudgetService.add → _rewrite → TransactionRepository.replace_all → atomic_text`가 핵심 경로입니다.

### 단계 A. 화면에서 값을 받기

`_add`는 `list_categories`로 현재 카테고리를 읽습니다. 비어 있으면 등록 안내를 하고 중단합니다. 목록을 가져오는 동안에만 잠금을 쓰며, 사용자의 답변을 기다리는 동안에는 잠금을 잡고 있지 않습니다.

`prompt(label, parse)`는 필드 하나를 입력받는 재입력 반복문입니다. 두 번째 인자인 `parse`는 문자열을 검사·변환할 함수입니다. 날짜는 `validate_date`, 금액은 `parse_amount` 등을 전달합니다.

```text
input() 결과: "15000"                 문자열
  → parse_amount: 공백 정리·숫자 검사
  → int(...): 15000                   정수
  → validate_amount: 양수 정수 검사
  → _add의 amount 변수: 15000
```

태그는 `"meal, lunch,meal" → ('meal', 'lunch')`로 변환합니다. 공백과 중복을 정리하지만 `Meal`과 `meal`을 같은 태그로 합치지는 않습니다. 메모는 선택 문자열이며 CLI에서는 한 줄 입력을 받고 CSV에서는 여러 줄 메모도 받을 수 있습니다.

`prompt`는 `ValidationError`만 잡아 같은 질문을 반복합니다. EOF/Ctrl+C는 바깥 오류 데코레이터까지 전달합니다. 따라서 취소를 잘못된 입력처럼 계속 재질문하지 않습니다.

### 단계 B. 서비스에서 실제 저장 준비

`BudgetService.add`는 키워드 인자로 정리된 값을 받습니다. `Transaction(id='pending', ...)`을 만들어 값 자체를 먼저 검사합니다. `pending`은 검증용 임시 ID이며 파일에 저장되지 않습니다.

`@dataclass`가 만든 초기화 후 `Transaction.__post_init__`이 실행되어 날짜·타입·금액 등을 검사합니다. 카테고리 이름의 형식은 모델이 검사하지만, 그 이름이 등록돼 있는지는 파일을 읽는 서비스가 검사합니다. **객체가 만들어졌다는 것과 파일에 저장됐다는 것은 다릅니다.**

그다음 `with self.store.session():` 안에서 다음 작업을 합니다.

```text
카테고리 다시 읽기 → 등록 여부 재확인
  → _inspect: 기존 거래 ID 중복·카테고리 참조 검사
  → _new_id: 기존 ID와 겹치지 않는 UUID 기반 ID 생성
  → replace(draft, id=...): 실제 ID의 새 Transaction 생성·재검증
  → _rewrite: 새 거래를 최신순 위치에 삽입해 파일 재작성
```

카테고리를 다시 읽는 이유는 사용자 입력을 기다리는 동안 다른 앱 작업이 목록을 바꿨을 수 있기 때문입니다. `_inspect`의 ID 집합은 거래 수에 비례하는 메모리를 사용합니다. 이 검사는 목록 조회에는 호출하지 않습니다.

저장·세션 정리가 성공한 뒤 `Transaction`을 CLI로 반환하고, CLI가 그 ID를 출력합니다. 저장 후 출력 실패가 발생할 수 있으므로 실패 메시지만 보고 무조건 재추가하면 중복 거래를 만들 수 있습니다. 먼저 목록을 확인합니다.

## 4. 파일 읽기: list/search는 언제 실행되는가

호출 경로와 데이터 전달 방향은 반대로 생각하면 이해하기 쉽습니다.

```text
출력 측이 다음 거래를 요청
print_transactions
  → list_transactions / search
    → _checked_transactions
      → iter_transactions
        → iter_jsonl: 다음 줄 읽기
```

`iter_jsonl`은 `(행 번호, JSON 사전)`을 전달합니다. `iter_transactions`는 사전을 `Transaction`으로 바꾸고 직전 거래와 정렬을 비교합니다. `_checked_transactions`는 카테고리 참조를 확인합니다. `search`는 조건이 맞으면 거래 하나를 전달하고, `print_transactions`가 바로 한 행을 출력합니다.

**제너레이터 함수 호출은 결과 전체를 계산하지 않습니다.** 함수 안에 `yield`가 있으면 호출 시 제너레이터 객체를 만들고, `for`나 `next()`로 소비할 때 본문을 진행합니다. `yield`는 값을 건넨 뒤 일시 정지하고 다음 요청에서 그 뒤부터 이어 갑니다.

`search`의 `matched += 1`도 `yield` 다음에 있으므로 소비자가 다음 값을 요청할 때 실행됩니다. 한도에 도달하면 다음 파일 행을 읽기 전에 종료합니다. `list_transactions`의 `yield from`은 검색 제너레이터로 값 요청과 종료를 위임합니다.

### 최신순과 메모리

파일 자체를 `(date, id)` 내림차순으로 저장하므로 조회 결과 전체에 `sorted()`를 호출할 필요가 없습니다. 검증된 `YYYY-MM-DD`는 같은 길이이므로 문자열 비교로 날짜 순서를 비교할 수 있습니다. 같은 날짜 안의 ID 비교는 생성 시각 순서를 의미하지 않습니다.

`SearchFilter.matches`는 지정된 조건을 차례로 검사합니다. 하나라도 안 맞으면 `False`, 모두 맞으면 `True`입니다. `None`은 해당 조건을 사용하지 않는다는 뜻입니다. 메모의 `casefold`는 대소문자를 무시하는 비교이고, 태그는 튜플의 원소 전체가 정확히 일치해야 합니다.

거래 전체를 모으지 않지만 카테고리 집합은 읽습니다. `--limit` 뒤에 있는 손상이나 다른 날짜에 반복된 ID를 모든 조회에서 전부 확인하는 것은 아닙니다. 전역 ID 검사는 거래 변경 전 `_inspect`가 담당합니다.

### 조기 종료 시 자원 정리

`with closing(generator)`는 해당 범위를 벗어날 때 `.close()`를 호출합니다. 제너레이터 안의 `with`·`finally`도 정리되어 파일과 잠금이 닫힙니다. 그래서 소비를 중간에 멈춰도 열린 자원이 남지 않게 합니다. `closing`에 넘기는 타입을 일반 `Iterator`보다 구체적인 `Generator[..., None, None]`으로 표현한 이유입니다.

## 5. 수정·삭제는 왜 파일을 다시 쓰는가

거래는 파일의 가변 길이 텍스트 행입니다. 중간 행의 길이를 바꾸면서 나머지 바이트를 안전하게 유지하려면 별도 처리 전략이 필요합니다. 이 구현은 전체 결과를 임시 파일에 다시 쓰는 방식을 택했습니다.

`update(identifier, **changes)`는 ID와 지정한 수정값을 받습니다. `changes`는 `{'amount': 55000}` 같은 사전입니다. 허용 필드와 대상 ID를 확인하고 `dataclasses.replace`로 변경된 새 객체를 생성합니다. `frozen=True` 때문에 원래 객체의 필드를 직접 바꾸지 않습니다. 새 객체도 모델 검증을 다시 통과해야 합니다.

CLI 파서의 `argparse.SUPPRESS`는 생략한 수정 옵션을 결과에 만들지 않습니다. 따라서 `--amount`만 주었을 때 다른 필드를 `None`으로 덮어쓰지 않습니다. 반면 `--memo ""`는 실제로 빈 문자열을 넘겨 메모를 지웁니다.

`_rewrite`는 세 작업을 같은 정렬 규칙으로 처리합니다.

| 호출 | excluded | replacement | 결과 |
|---|---|---|---|
| add | 없음 | 새 거래 | 새 거래 삽입 |
| update | 원래 ID | 수정 사본 | 원래 거래 제외 후 새 위치에 삽입 |
| delete | 삭제 ID | 없음 | 해당 거래만 제외 |

내부 `merged`는 기존 거래를 순서대로 읽습니다. 제외 ID면 `continue`하여 내보내지 않습니다. 새 거래가 현재 거래보다 최신이면 새 거래를 먼저 `yield`하고 `inserted=True`로 표시해 중복 삽입을 막습니다. 가장 오래됐거나 파일이 비었으면 반복문 끝에서 삽입합니다.

예: 기존 날짜가 `10-07, 10-05, 10-01`일 때 `10-06` 거래는 `10-07` 다음, `10-05` 전에 삽입됩니다. 출력 스트림이 곧 새 파일의 순서입니다. 마지막 거래를 삭제하면 세 파일 중 거래 파일만 빈 상태로 남습니다.

## 6. atomic_text와 session의 yield는 무엇이 다른가

일반 조회 제너레이터의 `yield`는 거래를 여러 번 전달합니다. 반면 `@contextmanager`가 붙은 `atomic_text`와 `session`은 **with 본문을 실행할 위치를 한 번 제공**합니다.

```text
with atomic_text(path) as stream:
    여러 거래를 stream에 기록

atomic_text의 실제 순서:
  임시 파일 생성·열기
  → yield stream          호출자의 with 본문 실행
  → flush / fsync         본문이 정상 종료했을 때
  → 파일 닫기
  → os.replace            원본 경로를 완성된 파일로 교체
  → finally               남은 임시 파일 정리
```

`mkstemp`는 원본과 같은 폴더에 임시 파일을 만듭니다. `fd`는 운영체제가 제공한 열린 파일 번호이며 `fdopen`으로 텍스트 스트림을 만듭니다. `flush`는 Python의 쓰기 버퍼를 내보내고 `fsync`는 파일 동기화를 요청합니다. 호출자의 쓰기에서 예외가 나면 정상 후처리로 계속 진행해 원본을 교체하지 않습니다.

`session`은 `.budget_app.lock`을 배타적으로 생성하고 초기화를 검사한 뒤 호출자의 파일 작업을 실행합니다. 정상·실패 모두 자신이 얻은 잠금을 정리합니다. 다른 작업의 잠금이 있으면 오류를 내며 그 잠금을 지우지 않습니다. 강제 종료로 남은 잠금을 자동 제거하지도 않습니다.

두 안전장치는 역할이 다릅니다. 잠금은 **동시 작업 충돌**, 원자적 교체는 **미완성 파일 노출**을 다룹니다. 정전 내구성·여러 파일의 동시 커밋·외부 편집기 변경까지 해결한 것은 아닙니다.

## 7. summary와 budget: 계산 후 출력 분리

`month_filter`는 `YYYY-MM`을 실제 시작일·마지막 날로 바꿉니다. `calendar.monthrange`를 사용해 윤년과 월별 일수를 처리합니다.

`summary`는 거래를 순회하며 해당 월의 `income`, `expense`, `count`와 카테고리별 지출 합계만 유지합니다. 모든 거래를 저장하는 리스트가 아닙니다. 지출 순위는 합계 내림차순, 같은 금액은 이름 오름차순으로 정렬한 뒤 TOP N을 고릅니다.

```text
수입 100000, 지출 15000, 예산 50000
  → MonthSummary(income=100000, expense=15000, budget=50000, ...)
  → balance: 100000 - 15000 = 85000
  → usage_percent: '30.0'
  → exceeded: False
  → print_summary가 화면 문자열로 출력
```

`@property`는 메서드를 `summary.balance`처럼 값 접근 형태로 읽게 합니다. 사용률은 큰 정수를 float로 바꾸지 않고 0.1% 단위 정수로 반올림한 뒤 문자열로 표현합니다. 예산 초과 여부는 표시용 반올림 값이 아니라 실제 정수 금액으로 비교합니다. 100.0%로 보이더라도 실제로 1원 초과라면 경고가 나올 수 있습니다.

`set_budget`은 해당 월만 변경하고 다른 월은 유지합니다. 예산은 실제 수입이 아닌 지출 한도입니다. 데이터가 없는 월도 예산이 있으면 사용률 0.0%와 데이터 없음 안내를 할 수 있습니다.

## 8. CSV: 읽기와 실제 반영 시점 분리

가져오기 경로:

```text
cli.main → BudgetService.import_csv
  → iter_csv: 헤더·행 구조·값 변환
  → 등록된 카테고리 확인·신규 ID·Transaction 생성
  → incoming 리스트에 신규 거래 보관
  → 전체 읽기 성공 후 정렬
  → heapq.merge(기존 스트림, 신규 목록)
  → replace_all → atomic_text → 최종 교체
```

`DictReader`가 CSV 인용 규칙을 해석합니다. 줄 전체가 아니라 읽어낸 `tags` 값에만 쉼표 분리를 적용합니다. `CSVTransactionInput(TypedDict)`는 사전의 키·값 타입을 설명하지만 입력을 자동 검증하지는 않습니다. 실제 검사는 변환 함수와 모델이 합니다.

모든 신규 행을 확인하기 전에는 거래 파일을 교체하지 않습니다. 한 행이라도 틀리면 0건 반영하고 첫 오류를 알립니다. 전체 신규 데이터를 모으므로 **가져오기 전체가 상수 메모리 스트리밍은 아닙니다.** `heapq.merge`는 이미 같은 기준으로 정렬된 두 입력을 차례로 합칩니다.

내보내기는 `export_filter`로 기간을 검증하고 내부 파일을 출력 경로로 쓰는지 확인합니다. `selected`가 기간에 맞는 거래만 전달하고 `export_rows`가 고정 헤더와 행을 기록합니다. 출력 대상도 임시 파일로 작성해 실패 전 기존 CSV를 보존합니다.

CSV는 ID를 포함하지 않으므로 다시 가져오면 새 ID입니다. 같은 내용을 두 번 가져오면 두 거래가 됩니다. 부분 성공·자동 중복 제거·완전한 백업 복원과 혼동하지 않습니다.

## 9. 오류는 어떻게 화면으로 돌아오는가

```text
validators / models / service / storage의 오류
  → AppError 계층: message + hint + exit_code
  → decorators.wrapped가 해당 오류 포착
  → show_error가 stderr에 원인·힌트 출력
  → 종료 코드 반환
  → __main__.py의 SystemExit
```

`ValidationError`는 2, `NotFoundError`·`ConflictError`·`StorageError`는 기본 1입니다. 일반 `OSError`도 데코레이터가 처리합니다. Ctrl+C/EOF는 130입니다. `@wraps`는 감싼 함수의 이름·문서·타입 힌트 등을 유지하고 `ParamSpec`은 원래 인자 형태를 타입 계약에 이어 줍니다.

파일 오류는 제너레이터를 만든 순간이 아니라 실제 순회 중에 날 수 있습니다. 그래서 생성 함수만이 아니라 순회·출력까지 포함하는 `main` 경계를 감쌉니다. CLI의 재입력 검증은 그 안쪽 `prompt`에서 먼저 처리합니다.

이것은 오류 메시지와 종료 코드의 공통 처리입니다. 데이터베이스 트랜잭션이나 이미 완료된 파일 교체를 자동으로 되돌리는 기능은 아닙니다.

## 10. 코드를 읽을 때 자주 만나는 표현

| 표현 | 이 프로그램에서의 뜻 |
|---|---|
| `self` | 현재 서비스·저장소·모델 객체의 상태에 접근 |
| `-> int`, `str \| None` | 반환/입력 타입 계약. None 허용 여부를 명시하며 런타임 검증은 별도 |
| `Literal['income', 'expense']` | 허용할 문자열을 타입으로 설명. 실제 값은 검증 함수가 검사 |
| `cast(...)` | 타입 검사기에 해석을 알려 줄 뿐 값 변환·검증이 아님 |
| `*` 뒤의 인자 | 호출 시 이름을 붙여 전달하여 필드 순서 혼동 방지 |
| `**changes` | 수정 필드 사전을 키워드 인자들로 전달 |
| `lambda` | 짧은 변환·정렬 기준 함수. 실행 흐름 자체를 새 계층으로 만들지 않음 |
| `with` | 시작·종료·실패 시 자원 정리 범위를 명시 |
| `yield` / `yield from` | 한 값씩 전달·일시 정지 / 다른 제너레이터에 위임 |
| `frozen=True` | 객체 필드의 일반적인 재할당 제한. 파일 안전성과는 다른 기능 |
| `_`로 시작하는 함수 | 외부 명령 API가 아닌 내부 보조 기능이라는 관례 |

## 11. 학습과 테스트를 연결하기

`tests/test_readme_workflows.py`는 README의 두 실행 경로를 실제 CLI 프로세스로 재현합니다. `tests/test_cli.py`는 명령과 오류·종료 코드, `tests/test_service.py`는 업무 규칙, `tests/test_storage.py`는 손상·쓰기 실패와 원본 보존, `tests/test_csv_io.py`는 CSV 경계 사례를 확인합니다.

제공 평가표는 기능뿐 아니라 계층 책임, 제너레이터·데코레이터·타입 힌트의 이유, 저장 형식과 병목·깨진 CSV 정책을 설명할 수 있는지 확인합니다. 함수의 주석은 설명을 돕는 근거이지 학습자의 이해를 대신하는 증거는 아닙니다. 제공되지 않은 배점이나 합격 조건은 추가하지 않습니다.

10만 건에서 조회는 전체 거래를 모으지 않지만 쓰기는 O(n) 검사·재작성이 필요합니다. import는 신규 정렬 O(m log m), 병합 O(n+m), ID 집합과 신규 거래의 메모리 O(n+m)을 사용합니다. n은 기존 거래, m은 신규 거래 수입니다. 카테고리 집계·정렬 비용도 별도입니다. 이전 측정은 해당 날짜의 보고서로 확인하며, 문서만 고쳤다고 새 성능 측정 결과가 생기는 것은 아닙니다.
