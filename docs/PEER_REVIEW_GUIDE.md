# 피어 평가 준비

기준은 사용자가 제공한 B2-1 평가 항목 1~4다. 아래 설명 주제는 준비를 위한 정리이며, 추가 합격 조건이나 실제 출제 문항을 의미하지 않는다. 구현·테스트 통과와 학습자의 이해는 별도 단계다.

## 항목 1 — 실제 기능과 데이터 유지

`tools.demo`는 카테고리 등록 → 수입·지출 추가 → 예산 → 요약 → 목록·검색 → 수정 → CSV 내보내기 → 잘못된 CSV 전체 미반영 → 사용 중 카테고리 삭제 거부 → 거래 삭제 → 가져오기 흐름을 실제 CLI 하위 프로세스로 시연한다.

수입 100,000원, 지출 15,000원, 예산 50,000원이면 잔액 85,000원과 사용률 30.0%가 나온다. 지출을 55,000원으로 수정하면 사용률 110.0%와 5,000원 초과 경고가 나온다. 영구 저장은 새로운 서비스 객체와 별도 CLI 프로세스로 다시 읽어서 확인한다.

테스트에서 오류의 stderr에 원인·힌트가 있는지, Traceback이 없는지, returncode가 비0인지 확인한다. 대화형 입력을 잘못했다가 고쳐 정상 저장하면 최종 종료는 0이다.

## 항목 2 — 책임 경계와 안전한 수정

CLI는 입력·출력, 서비스는 업무 규칙, 저장소는 파일 I/O, 모델은 데이터 구조와 값 검증을 담당한다. 카테고리 이름이 빈 문자열인지와 실제 등록된 카테고리인지는 서로 다른 계층의 검사다.

수정·삭제에서는 원본부터 비우지 않는다. 임시 파일에 전체 결과를 쓴 뒤 교체한다. 쓰기·동기화·교체 실패를 주입해 원본 바이트를 비교한다. 잠금과 원자적 교체는 서로 다른 안전장치다.

## 항목 3 — 핵심 기술의 실제 적용

제너레이터는 한 건씩 읽어 메모리 사용을 줄인다. 그러나 제너레이터를 sorted나 list로 모두 모으면 전체를 메모리에 올린다. 이 구현은 저장 순서를 최신순으로 유지하므로 조회 시 재정렬하지 않는다.

데코레이터는 CLI의 공통 오류 변환을 분리한다. 제너레이터 순회 중의 오류도 처리해야 하므로 main 실행 경계를 감싼다. `@dataclass`를 썼다는 것만으로 직접 구현한 공통 관심사 데코레이터 요구를 충족했다고 설명하면 안 된다.

타입 힌트는 계약을 표현하고 검증 함수는 실제 입력을 검사한다. `int`는 정수라는 의미일 뿐 양수 조건까지 표현하지 않으며, JSON 값을 cast한 것도 런타임 검증이 아니다.

## 항목 4 — 형식 선택과 실패 정책

JSONL은 숫자와 태그 배열을 그대로 표현하며 줄 단위 처리하기 쉽다. CSV도 스트리밍할 수 있으므로 "JSONL만 스트리밍 가능하다"는 설명은 틀리다. CSV는 외부 교환용으로 구분했다.

10만 건에서 조회 메모리는 작지만 쓰기는 전체 검사·재작성 비용이 있다. import는 신규 거래 정렬 버퍼와 ID 집합 때문에 메모리가 증가한다. 실제 측정값과 개선 제안을 구분해서 설명한다.

잘못된 CSV는 첫 오류의 위치·원인·힌트를 출력하고 이번 가져오기를 0건 반영한다. 부분 성공이나 자동 중복 제거가 아니다. CSV에는 ID가 없어 같은 파일을 다시 가져오면 내용 중복이 생길 수 있다.

## 학습 순서

GitHub에 반영된 `__main__.py`부터 시작한다. `cli.py`를 위에서 아래로 읽고, 한 거래의 입력값이 service → model/validators → storage로 이동하는 과정을 추적한다. 이후 list/search, update/delete, summary/budget, CSV 순으로 읽는다. 완성 코드 기준으로 설명하고, 별도의 퀴즈 답변을 다음 학습의 필수 조건으로 두지 않는다.
